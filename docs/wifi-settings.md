# Add or change Wi-Fi

Settings → Connections → Wi-Fi networks saves an inactive candidate. Only **Try network → Confirm trial** (or **Try again → Confirm trial**) starts a 120-second trial, without restarting Cool Eva. The service gate is sampled at admission and before every activation retry. Restarting or turning the bike on never starts a saved trial.

Before changing the access point itself, test the Bluetooth dashboard and activate any new Bluetooth key. Save the network details in that dashboard, change the hotspot/router, reconnect and read back over Bluetooth, then arm the trial. If the AP was changed first, use that tested Bluetooth link to enter/save the details. Otherwise restore the previous AP settings or bring up another already configured network before preparing Bluetooth. Password drafts must be re-entered when moving between pages: they never travel through a URL or browser storage.

The Pi joining a network and the phone reaching it are separate facts. The host phone opens the shown Pi address directly; a phone moving to a router first joins that Wi-Fi. A host that cannot reach its clients can use a second client on the new Wi-Fi. Only direct HTTP to the candidate's Wi-Fi address can **Keep network**. BLE and loopback cannot. Until then, the old profile stays saved, but a changed AP may no longer accept its credentials. **Use previous** cancels the trial and attempts the fallback; if necessary, restore the hotspot's previous name and password. **Cancel change** removes only an untried candidate. A failed candidate stays available for an explicit armed Try again, without retyping.

## Persistence and interruption

The private `/var/lib/cool-eva/state/network-trials.json` is root-owned mode 0600 and uses the service's acquired OS lock and serialized durable writer. It contains UUIDs, purpose metadata and outcome/confirmation phases, never a password. It is not rolled back with settings snapshots. Candidate profiles persist with autoconnect disabled and auth-retries 1. Both the watchdog and gesture recovery exclude their UUIDs, including candidates sharing the old SSID. The network reservation blocks owner edits/restarts while runtime hub learning continues without changing the choice revision. Only explicit confirmation enables autoconnect and auth-retries 0. Change inherits the old priority; Add uses the highest confirmed priority for its purpose, or 0 if no such profile exists.

A wlan0-only checkpoint (flags NONE) lasts 180 seconds, longer than the 120-second trial. Its D-Bus path is journalled so a restarted process can roll back its own checkpoint. A confirmation is journalled before destroying that checkpoint. The checkpoint must be observably gone before promotion, purpose/hotspot identity update, and finally retirement of the specifically replaced profile. Each phase resumes after a cut. A resumed success says that Wi-Fi may switch at power-on. Plain startup can complete an already accepted confirmation or restore an interrupted trial; it cannot authorise a new trial.

NetworkManager D-Bus carries secrets in-process; no password enters HTTP replies, logs, error messages, diagnostics or command arguments. Keep saved password uses GetSecrets server-side. Show/Hide only affects the new local draft. See the primary [connection API](https://www.networkmanager.dev/docs/api/latest/gdbus-org.freedesktop.NetworkManager.Settings.Connection.html) and [checkpoint API](https://www.networkmanager.dev/docs/api/latest/gdbus-org.freedesktop.NetworkManager.html).

## Image backend and installer hand-off (#324)

Bookworm's manual profiles use `/etc/NetworkManager/system-connections`. Raspberry Pi's Trixie integration round-trips `netplan-` profiles to authoritative `/etc/netplan` YAML; `/run/NetworkManager/system-connections` alone is not durable. The adapter preserves that backend, verifies the authoritative UUID after save/update/delete and flushes protected files/directories. Unsupported or unverifiable sources refuse mutation. These implementation checks do not establish the image's native semantics: **real-Pi acceptance is required before merge**. [Raspberry Pi's backend description](https://www.raspberrypi.com/news/cloud-init-on-raspberry-pi-os/).

After creating its initial confirmed profiles, #324 passes a UUID-to-purpose object (`home` / `hotspot`) on stdin to `node --experimental-strip-types scripts/configure-network-purposes.ts`, as root with Cool Eva stopped. The helper takes the same OS lock, reconciles a previously accepted/interrupted change, preserves an untried candidate and registers only existing confirmed UUIDs. It never authorises a trial. Existing unmapped profiles stay usable and get a purpose on Change. Installer credentials continue through NetworkManager's protected D-Bus backend, never this helper's argv.

Before route-C repair changes profiles while the service runs, call the CSRF/generation/revision-protected `POST /settings/networks/maintenance` and read its result, then stop the service and take the offline lock. Failure blocks profile replacement. Offline repair invokes the helper **before** changing profiles to reconcile a trial, then again to register the result. A re-image is a new instance; restoring settings also restores/reconciles network-trials.json. The updater preserves this file across software/settings rollback. Missing or foreign trial state never grants permission to activate a candidate.
