# Service parameter catalogue

`GET /service-catalogue` supplies the approved Service browser with every parameter identity and group from the active parameter table, and every signal identity, group and unit from the signal registry. It works before the bike has been read. It takes no bus or saved snapshot and returns no readings. Responses are not cached because a completed parameter read can select a different table while the page is open.

The parameter index remains the catalogue identity: four names describe two rows each. Those eight rows and the config word that only supports named bit writes remain read-only in the numeric editor. Numeric bounds come from the existing write target, including its narrower curated policy, or the storage type for a read-only row. The catalogue cannot widen the write codec's policy. The write runner still checks its live gate, table identity, compare-and-swap and readback for every confirmed parameter.

Units are limited to facts already established in the repository: `MAX_DC_CHG_CURRENT` uses amperes; `TORQUE_LIMIT` and `REGEN_TORQUE_LIMIT` use tenths of a newton metre (the existing curated write formatters in `src/vcu/write-targets.ts`); `BEAM_MAX_CURR_TH` uses milliamperes ([the measured light threshold](headlight-beam-threshold.md)). Other values remain raw. In particular, the local manufacturer-definition notes leave map power unresolved; the sketch's synthetic horsepower example is not a scale definition.

The catalogue returns unknown stock as `null`. `params.ecf` carries another bike's values, explicitly recorded as `otherBikeValue` in `src/vcu/param-file.ts`; they cannot fill a field labelled Stock. Current readings come separately from a saved sweep or a parameter read and retain their source identity.

## Approved Service page

Service is one scrolling page under More. Write parameters groups search, browse, the numeric editor and backup import/export. Service actions and Recent changes share a separate section; Current CAN values remains its own disclosure. The separate raw snapshot, read-sweep controls and parameter-table page are removed. Existing `#all` links open the same Service page with Current CAN values expanded; `params.html` redirects to Service. Lifetime statistics retain their existing Bike home until its cleanup.

The page has no global write-readiness caption. A valid differing numeric edit that is blocked shows one short line beside its disabled Confirm control, only while that edit matters. The existing admission, arm/dwell, compare-and-swap and readback checks remain unchanged; the caption never authorises a write.

Opening Service loads the read-only catalogue, compact write status, parameter-read status and saved snapshot. An unconfirmed table starts the existing safe parameter read automatically when it can help and its existing gates allow it. A confirmed table does not start another sweep. Selecting a parameter reads that exact micro/bank/index using the existing probe endpoint. Names, indices, micro and table must match; failed reads and unverified writes invalidate older current values rather than reviving a snapshot. Current readings are integer raw counts, displayed only with the established scales above.

A numeric edit uses the shared operation lock and two-tap 400 ms arm. The first tap refreshes status and the live value; a changed value requires a new first tap. The second tap sends one existing `action=parameter` request with that fresh value as `expected`. Only a successful matching per-parameter readback confirms the change. A lost reply has unknown delivery; no previous request's success fills its place. Active table replacement clears obsolete selections and backup rows. Status replies use request order, and metadata realignment has a fixed retry bound.

Backup CSV uses `id_hex,name,value` and raw integer counts, matching the existing exported format. Import matches index and name exactly, rejects duplicates and out-of-policy values, reads each entry freshly, and shows only differing values. Each row has its own confirmation and one parameter write plus readback. There is no bulk apply or backup batch write. Unchanged values send nothing. Export includes only known current readings; unknown values are never invented.

Failed selected-parameter reads and backup imports show a short visible reason in their existing feedback row. Full error detail remains in the status title; a rejected reading never becomes a plausible current value.

The single lights control uses the existing fixed five-circuit write action and its individual compare-and-swap/readbacks. It retains this bike's healthy light thresholds for restore. The other Service actions keep their existing confirmation tokens, GPS-clock check, parked/busy gates and charging restriction on restart. An accepted fault-clear without erasure evidence remains unconfirmed. Service results use the approved short feedback, with the server's detailed reason in the status title. Recent changes records only confirmed parameter readbacks in this browser session.

Current CAN values browses the complete registry, including never-seen values as `—`. Each row binds to its own filtered reading and fault state. Physical-range rejection renders `fault`; link loss and sensor age retain stale styling. Neither these rows nor the parameter editor invent values to match the synthetic sketch. Historical findings from the removed implementation and source checks are preserved in [service-legacy.md](service-legacy.md).

`check-service-parameters.ts` exercises the actual client models and CSV codec with typed synthetic HTTP responses. It covers identity, units, lock/dwell, compare-and-swap, each readback failure, status ordering, bounded metadata replacement, individual backup writes and Service actions. The phone-width gate exercises actual DOM controls, failure feedback, keyboard repeat, disclosures, exact requests, complete registry and both phone themes. The existing server write and simulator-refusal suites remain authoritative for bike-side gates.
