# 0x410 — the cluster's hub-protocol stream

`src/can/gps.ts` (the GPS multiplex), `src/can/hub-output.ts` (type 3), `src/can/hub-mirror.ts` (the diagnostics types).

**Three readers, two dispatch sites, and the split is by purity rather than by id.** The two pure decoders compose inside one `case` in `src/can/decode.ts`; the mirror writes the ride log and the diagnostics side-channel, so it cannot live in `decodeFrame`, which this repo keeps pure and replayable — `src/index.ts` calls it directly and deliberately does not return afterwards, or CAN GPS would silently disappear. Each reader tests byte 0 for itself, which is one comparison and is load-bearing on the BLE path too, where there is no demultiplexer to hang it on. This paragraph is the authority for that arrangement; the code carries a pointer, not the argument.

## 🚨 The emitter is the INSTRUMENT CLUSTER, not the Connectivity Hub

This repo said, in nine places, that "the hub echoes its own Bluetooth messages onto the VDB bus". **That is backwards.** From the COBO cluster firmware (#224):

- `0x000528A0` is `li r4, 0x410` with `li r3, 0` and `li r5, 8` into the single `CAN_Send` at `0x00099594`. The cluster transmits this id.
- The payload is copied from a contiguous block at `r13-0x746a … -0x7472`, written from ~18 sites whose byte-0 literals are `{0, 1, 2, 3, 4, 0x19, 0x1A, 0x1C, 0x1E, 0x1F, 0x21, 0x23}` — the hub message types.
- The hub reaches the cluster over **UART** (`UART_Port1_isr`), not CAN.

So the hub is the _Bluetooth transport_ for these records, not their author.

**And the cluster does not forward bytes — it synthesises the message.** The type-2 builder at `0x00062388` fills each slot from a different one of the cluster's own variables: SOC from the u32 at `r13-0x74f0`, vehicle state from `-0x74f9`, substate from `-0x74f8`, range from the u16 at `-0x7a6e`, pack temperature from `-0x79ca`. Nothing is memcpy'd from a UART buffer. **The CAN copy and the BLE copy of the same message type can therefore disagree**, which is a sharper statement than the one this repo used to make and the reason the two transports keep separate signal keys.

✅ **The decoders were right and are unchanged.** The framing really is byte-identical to the BLE records, and `src/can/gps.ts`'s measurement still holds: with the service stopped and no BLE session at all, 30 s of capture carried 58 × `1A 00`, 58 × `1A 01`, 58 × `1A FE` and 59 × `00 FF`. Position on CAN does not depend on the Bluetooth link. Only the provenance sentence was wrong.

The seed is the cluster's too: `0x00061D28`-`0x00061D60` loads `0xAAAAAAAA`, `0x55555555` and `0xC1A0BABE`, `0x00061D70` computes the swap-adjacent-bits transform, and the result goes out as `00 FF <seed LE32> 00 00`. That is `computeSessionKey()` in `src/ble/protocol.ts` — ⚠️ with one difference, see [the open discrepancy](#open-the-shift-in-computesessionkey).

## Sub-types present on the bus

Measured here over **5 494 s of `capture-20260809-161310-edcdcf23.log`, 78 056 frames** — only **three** sub-types appear:

| byte 0             | frames | rate over the capture                 |
| ------------------ | ------ | ------------------------------------- |
| `03` drive triple  | 43 417 | 7.9 Hz                                |
| `1A` GPS multiplex | 29 829 | 5.4 Hz (= ~1.8 Hz × three sub-frames) |
| `00` seed          | 4 810  | 0.9 Hz                                |

A separate 7 141-frame census by the `cluster-ids-capture` pane, on a different file, found **eight**: `03` 3796 · `1A` 2417 · `00` 812 · `02` 79 · `04` 16 · `1F` 7 · `19` 7 · `01` 7 — every one inside the firmware's twelve literals and none outside (`1C`, `1E`, `21`, `23` unseen). ⚠️ An earlier draft of this file presented that census as "a 60 s riding capture"; it is neither 60 s nor mine. Types `02` and `04` are **absent entirely** from the 5 494 s measured above, so no rate for them is quoted here.

⚠️ **They are not always on the bus.** `evidence/cluster-ids-20260915T153020Z.log` — 25 s parked on AC — carries **no `0x410` at all**, and neither does the 2.4 GB `capture-20260803` archive file. Type 3 in particular only appears while the bike is moving. Decoding it adds signals that are absent at rest; that is the frame's behaviour, not a fault.

Types 2 and 4 stay undecoded: they are rare — absent from the 5 494 s above, and under 0.2 Hz where they do appear — and they duplicate `0x101` and `0x104`, which arrive at 100 Hz.

## Type 3 — the drive triple

`src/can/hub-output.ts`.

⚠️ **Rate, stated three ways because one number misleads.** 7.9 Hz averaged over the whole capture (which is mostly stationary), **17.8 Hz** over the 2 435 s spanned by the type-3 frames themselves, and a **median inter-frame gap of 49.1 ms — 20.4 Hz — while it is actually streaming**. An earlier draft said "~8.8 Hz", from 530 frames of a 60 s window that included standing still. The builder at `0x0006262C`-`0x00062674` writes three 16-bit fields, each as two halves of one source variable:

| bytes | source              | signal                      |
| ----- | ------------------- | --------------------------- |
| b2-b3 | u16 at `r13-0x7a12` | **`dash_speed_kmh`** 🟡     |
| b4-b5 | u16 at `r13-0x7a0e` | motor rpm (feeds the power) |
| b6-b7 | i16 at `r13-0x7a9c` | **`motor_torque_can_nm`**   |

Torque is **signed, measured not assumed**: b7 is `0xFF` on 5 471 of 43 417 frames — that is regen.

### 🟡 `dash_speed_kmh` is NOT `speed_can_kmh`

Against 547 364 `0x104` frames from the same capture, paired within 50 ms:

|                                                            |                                   |
| ---------------------------------------------------------- | --------------------------------- |
| b2 == `floor(speed_can_kmh)`                               | **3.1 % exact, 10.4 % within ±1** |
| b2 / `speed_can_kmh`, median over 42 705 samples ≥ 20 km/h | **1.0433**                        |
| `motor_rpm_can` / b2, median                               | **40.26**                         |
| `motor_rpm_can` / `speed_can_kmh`                          | **42.0 exactly**                  |

It is the same geared driveline speed through a **different divisor**, ~4.3 % higher. Since `speed_can_kmh` already over-reads GPS by +3.5 %, this number sits ~8 % above GPS — where a legal speedometer sits, because a speedometer may not under-read.

❓ **Whether it is literally the number on the dash is UNCONFIRMED.** It is an inference from the ratio and from which ECU emits the frame. One glance at the speedo against the phone on the next ride settles it. This bears directly on the driveline decomposition that `can-decode-findings.md` records as not settled.

⚠️ **An earlier draft claimed 96.6 % agreement with `speed_can_kmh`.** That came from 60 seconds at 10-12 km/h, where a 4 % difference is smaller than one count. The full-ride numbers above supersede it — the same trap `can-decode-findings.md` warns about for `0x104`.

⚠️ **b3 is `0x00` in all 43 417 type-3 frames** — the bike cannot go fast enough to set it. The u16 width comes from the firmware writing both halves from one variable, not from the bus, and `scripts/check-cluster-frames.ts` holds that byte with its one deliberately synthetic fixture.

## Open: the shift in `computeSessionKey`

`0x00061D84` is `srwi r4, r0, 1` — a **logical** shift. `src/ble/protocol.ts` uses JS `>>`, which sign-extends because `seed & 0xaaaaaaaa` is a negative int32 when bit 31 is set. They differ iff seed bit 31 is set and bit 30 is clear — **25 % of seeds**.

The constant `0xC1A0BABE` is confirmed; the shift is not. This is deliberately **not** fixed here: the handshake is validated working on the bike, and `protocol.ts` notes that a wrong key produces "no error, just endless re-seeding" — which is exactly how a 25 %-of-sessions failure would hide. It needs a live BLE test (log seeds and re-seed counts over a dozen sessions; a quarter should fall in the disagreeing class), not a quiet edit inside a decode change.
