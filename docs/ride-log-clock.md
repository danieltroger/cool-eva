# The ride log on a machine with no clock

The Pi has no RTC and loses power with the bike, so between boot and the first clock step the wall clock is whatever the kernel started with. `src/storage/encrypted-log.ts` named its files from that clock, which is how `rides-2060-08-08.celog` came to hold 274 KB of real day-one riding — and `rides-2060-02-16.celog` beside it, which nobody had noticed.

Issue [#188](https://github.com/danieltroger/cool-eva/issues/188). Every figure here is generated by `evidence/keyoff/clock-figures.py` or `capture-figures.py` and appears in `evidence/keyoff/figures.txt`, their committed output, so a number can be checked without the corpora. ⚠️ Two do not, and are marked where they appear: session 130's five jumps, and the count of stepped sessions carrying no GPS row at all. Both are one-off queries over the same database.

## 1. How big the problem is

Over `rides.db` as of 2026-09-13 — 35 168 921 readings across 130 boots:

|  |  |
| --- | --- |
| boots starting with the clock more than 60 s wrong | **75 of 130**, 74 of them stepping exactly once |
| how long the clock stays wrong | **3.7 s to 2 374.0 s, median 15.9 s** |
| readings stamped before the step | **257 096** |
| boots whose pre-step readings cross a date boundary | **9** |
| boots where a segment was therefore sealed under the **wrong file name** | **6** |
| boots that never log a GPS fix at all | **46**, holding 1 902 119 readings |

⚠️ **The detector is an upper bound, not a measurement.** It calls a >60 s jump between consecutive `seq` a clock step, and that is also exactly what log-on-change produces when nothing changes for a minute. Session 130 has five such jumps across 24 readings, which no clock did (⚠️ a one-off query, not in `figures.txt`). The floor is the corroborated subset in §4: **40 boots** where a GPS reading proves the step happened and how big it was.

🔥 **The median untrusted window is 15.9 s and the segment timer is 30 s.** For the median boot, every wrongly-stamped reading therefore sits in a segment that is sealed _after_ the clock is fixed. That is why the trust is recorded **per reading, when the reading is queued**, and not sampled when the segment is sealed: a seal-time sample would mark the median boot's whole pre-step run as trustworthy. On the corroborated subset the window is a median of 22.1 s with 18 of 40 past the interval, so the margin is real but thinner than the headline suggests.

⚠️ And the window statistic says _how much_ a seal-time sample gets wrong, not _whether_: the segment that straddles the step is mislabelled in **every** stepped boot regardless of how long the window was. The first version of this sentence had that backwards.

## 2. What the code does

`src/storage/trust-runs.ts` splits a buffer into runs of equal trust; `encrypted-log.ts` seals one segment per run and chooses the file from the run's trust.

| trust                       | file                                   |
| --------------------------- | -------------------------------------- |
| `satellite-backed`          | `rides-<YYYY-MM-DD>.celog` — as before |
| `never-synced`, `contested` | `rides-boot-<sessionId>.celog`         |

`sessionId` is the existing 8-byte per-process random id that is already sealed into every segment header and already deliberately **not** a timestamp, so the name and the contents agree with no second source of truth. The "monotonic sequence" #188 asks for is `seq`, which is on every row already.

The header goes to `{ v: 3, session, trust, signals }`. Additive: `scripts/decrypt-log.ts` never reads `v` at all, so v1 and v2 segments in the same directory decode unchanged and report no trust — which is _unknown_, not _good_.

### Nothing is deferred, and that is the point

#188 offers "defer opening the day file until the clock is stepped" as an alternative. **Refused.** 46 of 130 boots never see a GPS fix, so on those the clock is never confirmed and a deferral would buffer the entire session in RAM — up to 557 475 readings — waiting for an event that never comes, on a machine whose power cut is not a risk but a certainty. A cut during the buffer would cost the whole ride. Writing immediately under an honest name costs a file.

### What it costs, stated rather than discovered

Every boot has at least the few seconds before the first corroborated fix, so **every boot writes a boot file** — with one escape hatch: `GPS_TIME_SYNC=0` makes `systemClockTrust()` answer `satellite-backed` unconditionally (`src/gps/clock.ts`), which is right on a bench with NTP and means no boot file at all there. On the bike: **130 boots over 23.9 days — 5.43 a day, about 1 983 a year.** Most are small, but the 46 GPS-less boots put their whole session in one, a median of 3 693 readings and at most 557 475 — **1 902 119 of 28 790 572 readings, 6.6 %**, before counting the pre-step rows of the boots that do sync.

- **Nothing prunes them.** No code in `src/` deletes a `.celog`; they leave with the day files when the directory is swept to the laptop, by hand, like everything else here.
- `/status` counts and `stat`s every `.celog`, so its `log.files` number roughly triples. That is fetched when the settings sheet is opened, not on a timer, so it is an on-demand cost.
- ⚠️ **`/dl` stops being byte-ordered by time.** It concatenates by `.sort()`, and `rides-boot-*` sorts after every `rides-2026-*`. That property is what dated the NUL holes in `docs/power-cuts.md` §7 by byte offset; from here on that technique works only on dumps taken before this change. Segments are self-framing and every row carries `session` + `seq`, so nothing is harder to _read_ — only harder to locate by offset.

Two alternatives were weighed and are recorded rather than argued again: one permanent `rides-untrusted.celog` (one file ever, but it never leaves in the ordinary sweep and has to be truncated by hand), and the kernel `boot_id` instead of the session id (it would tie a `.celog` to the capture of the same boot, which is genuinely useful — but it is Linux-only, needs a fallback branch for the checks, and adds a second source of truth for a name whose contents already carry the identity).

## 3. What is still wrong, and what is not

✅ Fixed: the file name no longer asserts a date nothing supports, and every reading says which clock stamped it, in the log and in `rides.db`'s `reading.clock_trust`.

❌ **Not fixed: `ts` is still wrong on pre-step readings, and is left that way on purpose.** Forcing timestamps to agree recovers ordering by destroying time — it would drag every good row after a forward step up to 2060 and pin it there. `seq` is what orders the log, and it is never derived from a clock. `scripts/decrypt-log.ts` reports and does not repair.

❌ **Not fixed: mtimes.** A file created under a wrong clock carries a wrong mtime, and nothing in the writing process can change that. Within a boot, sort by name; across boots, `ls -t` is not evidence.

## 4. Recovering the real time, and how well it works

`gps_epoch_s` is recorded **raw**, against each row's own wrong stamp — `src/gps/clock.ts` says so, and refuses to log a derived copy of the drift for exactly this reason. So the offset is already in the data:

```sql
-- for one session, using the last GPS reading before the step
SELECT (value * 1000 - ts) / 1000.0 AS offset_seconds
FROM reading r JOIN signal s ON s.id = r.signal_id
WHERE s.key = 'gps_epoch_s' AND r.session_id = ? AND r.seq < ?
ORDER BY r.seq DESC LIMIT 1;
```

Add `offset_seconds` to every pre-step row of that session.

✅ **Validated on 40 of 40.** Of the 75 stepped boots, 40 carry a pre-step `gps_epoch_s` row, and on every one the recovered offset matches the measured step: **0.001–1.535 s, median 0.235 s**. The other 35 have no pre-step GPS row — 14 have none in the whole session (⚠️ also a one-off query) — so their step was not ours. `systemd-timesyncd` over the hotspot is the obvious candidate; nothing here settles it, and "it was never a step at all" is the other candidate the detector cannot rule out.

## 5. The capture filename

`scripts/can-capture/capture.sh` names captures `capture-<date>-<time>-<bootid>-<uptime>.log`.

The **uptime** is new and is the only monotonic thing a machine without an RTC has: it orders two captures from one boot correctly even when the clock steps between them. Padded to eight digits, so the padding has no expiry date the bike can outlive.

⚠️ **The date stays first**, and that is a decision made against a measurement — but a much smaller one than the first version of this sentence claimed. Sorting a boot's files by the name's date agrees with sorting them by their own first frame with **0 disagreements — out of 6**. ⚠️ Six is the whole comparable population: of the 81 boots with a frame-carrying capture, only **6 have more than one**, so in the other 75 there is nothing to order. So the hazard a boot-id-first name would fix has never fired in the six places it could have, while the reorder would cost a chronological `ls` over the whole archive forever and leave one directory carrying two naming schemes. That is thin evidence, and it is why this is a reversible naming choice rather than a claim.

The boot id and the uptime also go **inside** the file, on a `# boot … uptime …` first line — the same argument #185 used to keep `2>&1`: the archive travels to the laptop and the journal stays on a card that gets reflashed, so anything not in the file is lost. `scripts/replay-capture.ts` counts a line it cannot parse as `framesSkipped`, so it costs a reader nothing.
