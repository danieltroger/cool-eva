# Bundle updates and automatic rollback

Bundle installs use the system shell, `jq`, `flock`, GNU coreutils/tar, zstd and curl. The updater never invokes Git, npm or the candidate's Node to recover a trial. The bundled Node is used for native preflight and the old reader's settings compatibility check. An upstream lockfile change cannot refuse a bundle update. Checkouts retain the existing owner-run, fast-forward-only Git updater until the installer switches them to bundles.

Before writing any bundle unit or invoking `initialise`, the installer runs `apt-get install -y jq` and `apt-mark manual jq`. Lite does not supply jq; marking it manual prevents dependency cleanup from removing it. Daniel's first route-C migration performs these same steps before switching his service. This is an installer requirement, not an extra rider command.

This PR supplies the updater and dormant bundle units. It does not install them on an existing checkout. #317 owns the data layout, settings store, runtime storage cutover and the only migration journal: [data-layout.md](data-layout.md). The updater checks settings/migration completion; it never moves a log, capture, parameter archive or Wi-Fi dump. `/var/lib/cool-eva/updater` holds its private journal, settings snapshots, download cache and edit archives; those are separate from `state/data-move.json`.

`/etc/cool-eva/update.json` is a root-owned 0600 file, written by the later installer:

```json
{
  "format": 1,
  "releaseRoot": "/opt/cool-eva",
  "dataRoot": "/var/lib/cool-eva",
  "settingsLock": "/run/cool-eva/settings.lock",
  "service": "cool-eva.service",
  "channel": "main",
  "healthUrl": "http://127.0.0.1/release-health"
}
```

The installer places releases under `/opt/cool-eva/releases`, creates the `current` link, verifies the service's migration and initial app health, then invokes `run.sh initialise`. The stable entry points are `/usr/local/libexec/cool-eva-update` (dispatcher) and `cool-eva-launch`. The app's bundle identity overrides a legacy `UPDATE_DIR`, so the button cannot accidentally fall back to updating a retained checkout. Editing the active release over SSH remains possible with `sudoedit`; the version shows the branch, commit and `+edited`.

Before replacement or cleanup, only inventoried files whose checksums changed are backed up, with a change list recording hashes and deletions. Untracked scratch files are not included. Each release has one archive; identical content is reused, and further edits replace that archive atomically. Keep the newest three archives, each at most 16 MiB (48 MiB retained total). Changed-file content is limited to 8 MiB; larger edits refuse the update before stopping the app and ask the owner to save/revert them over SSH. An interrupted archive cache is removed before the next update. Settings snapshots remain 0600 under the private directory and retain at most three, always including the current and pending rollback snapshots even when older than the extras.

The public button sends the existing `X-Cool-Eva: update` header, queues a separate systemd unit, and follows `/update-status` through the HTTP restart. It supplies no URL or version. A privileged SSH operator can run `cool-eva-update install-tag cool-eva-<release-id>` for a CI branch bundle; the normal button still follows the installed channel. Release discovery downloads `cool-eva-channels/<channel>.txt` from GitHub Releases, containing only an immutable `cool-eva-<release-id>` tag. All URLs are built under the fixed public repository. No unauthenticated GitHub API requests, HTML scraping or local Node installation are involved.

Bundle Update uses #317's shared `reserveSettingsRestart` gate before queueing: the same process generation, saved revision, parked/busy-bus rules and pending Bluetooth-key acknowledgement as checkout Update. The shared reservation holds the settings revision and bus during the bounded queue request and releases them on success or failure. It does not restart the app a second time or keep CAN reserved through the download. At the later external stop, the existing SIGTERM handler aborts writers, sweeps safely and seals the log; an admission already overtaken by SIGTERM leaves its lease held for that shutdown. A duplicate admission cannot release the first request's lease.

One `updater/update.lock` covers updates, boot repair and both rollback paths. Downloads have bounded size and time, validate the manifest, check sha256, refuse archive links/devices/traversal, verify the extracted inventory and load the native modules before stopping the app. Staging is on the release filesystem. Only directories and regular files enter the runtime payload. Cleanup retains current and previous code and removes interrupted download caches; it does not follow links or cross mounts, and refuses configured data paths inside code or the reserved updater directory. No checkout or shared data directory is deleted.

After stopping the app, the updater acquires #317's `/run/cool-eva/settings.lock`, snapshots `state/settings.json`, releases that lock and records the trial intent. A temporary symlink is renamed over `current`; journal files use write-then-rename, 0600 modes and storage barriers. The trial requires 60 continuous seconds of active service plus HTTP/settings health, measured from `/proc/uptime`. Missing physical CAN, BLE, GPIO or Wi-Fi readings do not fail an otherwise healthy parked installation. A failed trial restores the snapshot and explicitly selects the recorded previous release. A clean failed release is rejected once; an edited release is identified as edited and can be reinstalled from the same published tag.

The app unit creates `/run/cool-eva` as root 0700 before its recovery pre-start and preserves it across stops with `RuntimeDirectoryPreserve=yes`. Otherwise a boot repair would lack the settings-lock directory, or a stop/start could replace the inode that another writer locked. This follows the [v257 execution manual](https://github.com/systemd/systemd/blob/v257/man/systemd.exec.xml#L1469): preserved runtime directories survive stops and are recreated after reboot.

Systemd may unload an unreferenced stopped unit; unloading already clears its rate counter ([unit manual](https://github.com/systemd/systemd/blob/v257/man/systemd.unit.xml#L1208)). The start helper tolerates that specific `reset-failed` response and logs it; other reset errors remain fatal. Recovery can also select its recorded directory when the failed release's own metadata is damaged, without needing that release's Node or JSON to work.

The app's `ExecStartPre` attempts to repair a pending transaction before starting after a reboot. It skips repair while a live process holds the shared update lock. Boot recovery fails open: missing jq, updater permission drift or damaged updater JSON emits a loud **“RECOVERY FAILED”** log and starts the complete release selected by `current`. The unit also ignores a failed/missing dispatcher executable. The atomic link never selects half-extracted code. A failed recovery can leave a complete trial candidate running without update supervision; the next successful Update repairs its pending transaction first. Explicit `update`, `failure` and `repair` actions still fail closed.

A cut during a trial restores the previous release and settings, reports **“Update interrupted — press Update again”**, and does not reject the release. A cut during rollback replays the same recorded target. A cut after promotion repairs the link to the committed current target. A separate oneshot `cool-eva-update-repair.service`, triggered by the update job's own `OnFailure`, covers a killed/timed-out updater while the OS remains up, including restarting the app if it stopped before recording trial intent. It shares exactly the same lock and repair code; it is not a resident recovery server. Settings edits made during a failed trial can be lost; this snapshot is the single settings-protection mechanism.

After promotion, `Restart=on-failure`, `RestartSec=5`, `RestartMode=normal`, `StartLimitIntervalSec=120`, `StartLimitBurst=3` and `OnFailure=cool-eva-rollback.service` cover later crash loops. The handler requires terminal `SubState=failed`, nonzero `NRestarts` and an OS that is not shutting down. It works even if the limiter's journal line was dropped or reworded; neither that message nor a literal `Result=start-limit-hit` is required. An ordinary crash awaiting its automatic restart or a manual stop cannot trigger rollback. Four rapid manual/app restarts instead reset the failure counter and start the **current** release. Rollback consumes the previous target once and never exchanges links. A late rollback asks the previous code's actual read-only settings parser whether it can read today's document: compatible later changes are retained; only an unreadable document restores the pre-update snapshot. That restore can lose incompatible later settings changes, but never restores or deletes ride data. Slow crash loops whose complete restart cycle exceeds roughly 40 seconds may escape this 3-in-120-second guard and require a corrected release or SSH intervention.

These systemd details were checked in upstream v257 source, rather than inferred from a unit: [service.c](https://github.com/systemd/systemd/blob/v257/src/core/service.c#L2671) increments `s->n_restarts++` when queuing an automatic restart; [the start path](https://github.com/systemd/systemd/blob/v257/src/core/service.c#L2878) resets it for a nonautomatic start; [the limit path](https://github.com/systemd/systemd/blob/v257/src/core/service.c#L5434) enters `SERVICE_FAILURE_START_LIMIT_HIT`. The [unit manual](https://github.com/systemd/systemd/blob/v257/man/systemd.unit.xml#L1195) explicitly includes manual starts and documents `reset-failed`; the [service manual](https://github.com/systemd/systemd/blob/v257/man/systemd.service.xml#L936) explains why `normal` preserves failure handling while `direct` skips `OnFailure`.

The [dead-state path](https://github.com/systemd/systemd/blob/v257/src/core/service.c#L2076) replaces `s->result` only while it still equals `SERVICE_SUCCESS`, so a crash loop can exhaust the limit with `Result=exit-code`. The [limiter](https://github.com/systemd/systemd/blob/v257/src/core/unit.c#L1800) emits “Start request repeated too quickly.” Its [logging macro](https://github.com/systemd/systemd/blob/v257/src/core/unit.h#L1070) attaches the service and invocation fields, named `UNIT` and `INVOCATION_ID` by the [system manager](https://github.com/systemd/systemd/blob/v257/src/core/manager.c#L945). These explain the observed CI journal, but journal delivery is deliberately not a rollback prerequisite. The disposable Ubuntu CI runner uses v255; the target Raspberry Pi OS uses v257.

After app promotion, the helper files are copied to a new versioned directory outside releases, checked with `sh -n` and a read-only self-test, flushed and selected by atomic helper symlink. The previous helper remains available. The stable dispatcher tries the retained helper when syntax/self-test fails; after an action failure it invokes retained recovery, rather than retrying the update or swapping targets. Both helper generations must read journal protocol 1. The two small dispatcher/launcher entry points remain stable; changing that bootstrap contract requires rerunning a future installer that explicitly migrates it.

The existing version/status text says **“OS updated since this release was tested”** when the recorded kernel metapackage, firmware, BlueZ, NetworkManager, systemd, glibc or libstdc++ version differs from the package versions recorded on this Pi when the release passed health. Initialisation records the first healthy install after catch-up; each promotion records a new baseline atomically with its target, retaining the previous target's baseline for rollback. The original image's package list remains release provenance and does not drive the notice. This refreshes on demand, at most once a minute. Kernel-series, BlueZ or NetworkManager drift cannot be undone by a bundle rollback. Loss of GitHub access, a full/failing SD card or a removed apt dependency can still prevent an update; the running bundle remains installed, and the button reports the failure when the updater can record it. SD/controller corruption can damage code and data on the same card: separate directories are not a backup. Bundle rollback does not repair the OS or boot firmware.

`npm test` includes four portable fixture checks, requiring POSIX sh, jq and tar/zstd. They execute the real shell state machine and real archives with service/download adapters; macOS additionally adapts missing GNU commands and does not prove `flock` semantics or Linux durability. The separate `Bundle updater recovery` Actions job uses the actual Linux systemd limiter, `OnFailure`, shared `flock` and full 60-second trials: app startup despite each of the three updater faults, quiet promotion, simultaneous failure-handler request, four manual restarts, first synthetic CAN-frame crash after promotion with updater journal access disabled, offline rollback and a subsequent good update. It never contacts a Pi or CAN adapter. QEMU on the pinned Raspberry Pi OS image, physical hardware and actual SD power cuts are separate installer/release gates.

Publishing is still a later increment. Keep immutable release assets available, upload payloads before the manifest and update a channel pointer last. Only main can publish the main channel; PR builds are artifacts and are never published. The mutable `cool-eva-channels` release cannot enable GitHub immutable-release locking; replace its pointer only after all referenced assets are available. A glibc/libstdc++ comparison or the pinned-image QEMU gate is required before rider releases. Tests run only on changes/releases; no scheduled human maintenance or scheduled CI job is introduced.

APT security updates do not patch the private Node binary or bundled native modules. A security fix there requires Daniel to ship a new bundle; a rider using a frozen release may see no warning about it.
